<objective>
Close the reversibility gap (D-10, RMB-07): today linking a refund permanently recategorizes it
(`applyDetachCleanupTx` re-hashes/re-titles/re-categorizes its expense) with no way back. This plan
adds a pre-link snapshot recorded at link time and makes both unlink paths — remove one refund,
delete the whole reimbursement — restore that exact prior state.

Purpose: RMB-07 explicitly requires "unlinking a refund ... restores baseline — the refund
reappears as a normal inflow in its own month" — today's `deletePairByTransactionId` only removes
the LINK, never reverts the categorization side-effect `createPair` already applied.
Output: `reimbursement_refund_snapshot` table + migration; snapshot recorded on every link (create
and append); `deletePairByTransactionId` and a new `deleteReimbursementForAnchor` both restore
baseline via a shared helper; `removeRefundAction`/`deleteReimbursementAction` server actions (D-09's
two lifecycle actions).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| removeRefundAction / deleteReimbursementAction -> service | Both parse a raw id from FormData; ownership must be re-verified inside the service, not assumed from the UI having only shown the user's own data. |
| Restore path -> expense table write | Restoring a snapshot writes to an arbitrary expense row by id; a snapshot referencing another user's expense id must never be honored. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-75-07 | Elevation of Privilege | restoreRefundBaseline expense UPDATE | high | mitigate | The UPDATE's WHERE clause always includes `expense.userId = input.userId` in addition to the snapshot's expenseId — a cross-user snapshot reference (which should never exist given ownership-scoped inserts) still cannot mutate a foreign row even if it did. |
| T-75-08 | Repudiation | deleteReimbursementAction restore-then-delete ordering | high | mitigate | restoreRefundBaseline is called for every refund BEFORE the reimbursement row (and its cascading refund rows) is deleted, inside one db.transaction — a mid-loop failure rolls back the whole batch, never leaving some refunds restored and others not. |
| T-75-09 | Tampering | npm/pip/cargo installs | n/a | accept | No new package installs in this plan. |

</threat_model>
