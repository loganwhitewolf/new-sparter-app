<objective>
Prove the lens seam end-to-end on ONE path before fanning out to the remaining nine aggregation
sites and three routes: thread `?lens=cassa|competenza` through `/dashboard/overview`'s KPI totals
(`getOverviewAmountTotals`), render a global `LensSwitch` control next to the year selector, and
persist the choice via URL (canonical) + sessionStorage (restore layer), reusing the year-selector
pattern already shipped (PR #41 / ADR 0009-0010).

This plan also builds the SHARED infrastructure every later plan in this phase reuses: the
`LedgerRowSource` type + `resolveLedgerRowSource` helper (lib/dal/dashboard-filters.ts), the
`Lens` type + `parseLensParam` validator (lib/utils/search-params.ts), and the `LensSwitch`
component (components/dashboard/lens-switch.tsx) — built once here, rendered on all four dashboard
sub-routes by later plans.

Architecture is LOCKED by ADR 0019 §10: swap which Postgres VIEW an aggregation reads FROM
(`ledgerEntryCash` <-> `ledgerEntryAccrual`, both already exist from Phase 77) — never thread a
`lens` string into the aggregation's WHERE/amount logic. The amount is resolved INSIDE the view;
this task must never call `effectiveAmount()`/`isNotSecondary()` on a `ledgerRowSource` row.

Purpose: prove the seam-threading pattern is safe and reversible on a real path before touching
the other nine aggregation sites, so an architectural mistake surfaces after one commit, not ten.
Output: working cassa/competenza switch on the Overview page's KPI cards, backed by a real-Postgres
regression test proving both byte-identical cash and correct accrual behavior.
</objective>
