# Quick Plan: 260730-m2x — Amortization + dashboard fixes

## Goal

Three independent, small fixes:

1. "Ho ricevuto un rimborso" (`reducePlanTx`) links the refund to the original expense exactly like "vendita" (`realizePlanTx`) already does.
2. Deleting an amortization plan fully resets the row's client-side state so the transaction shows as amortizable again immediately, without a hard reload.
3. The dashboard month breakdown panel gets a link into the transactions list filtered for that month.

## Context

No separate `*-CONTEXT.md` — the user pre-locked these three decisions in the planning request. Investigated directly in the codebase; findings below.

**Bug 1 root cause.** `reducePlanTx` (`lib/services/amortization-lifecycle.ts`) deliberately skips `createPairTx` — the code comment calls this the "D-03 instead mechanic" and explicitly says "no v2.8 reimbursement link on the open-plan partial-refund path." `realizePlanTx` calls `createPairTx(tx, { anchor: { transactionId: plan.transactionId }, counterpartId: input.saleTransactionId })` right after closing the plan. `createPairTx` (`lib/services/transaction-pairs.ts`) resolves the anchor purely from the transaction's own `expenseId` — it does not care whether the plan is open or closed, so the same call is safe to add to `reducePlanTx` (which keeps the plan open).

**Bug 2 root cause — NOT a server bug.** Verified with a real-Postgres test against `getAmortizationEligibility` that after `reverseDetachTx` (called by `removeAmortizationPlan`), a transaction correctly becomes eligible again — including after a realize-with-sale, because the abandoned standalone expense (now with zero transactions) gets deleted by `reconcileExpensesAfterTransactionRemoval`, and `reimbursement.expenseId` has `onDelete: cascade`, so any linked reimbursement disappears with it. The actual bug is in the transactions **list** page's client state: `TransactionTable` seeds `loadedTransactions` via `useState(transactions)` once and never resyncs it from the `transactions` prop, so the `router.refresh()` called right after "Rimuovi ammortamento" is a no-op for this component's own state. `markAmortizationRemoved` only clears `amortizationPlanId` on the row, leaving `reimbursementId` stale — and `computeAmortizationEligibility` checks `reimbursementId != null` *before* `amortizationPlanId`, so the row keeps showing `reason: 'reimbursement'` (stuck / not amortizable) until a full page reload. This is already reachable today via "vendita" (which already links); Bug 1's fix makes it reachable via "rimborso" too — both fixes must ship together or Bug 2 regresses for the refund path. (The transaction **detail** page doesn't have this problem: `TransactionDetailClient` uses the `transaction` prop directly, no local copy, so `router.refresh()` there works correctly already.)

**Bug 3.** The dashboard has no month "popup" dialog — the closest thing is `OverviewMoversPanel` (`components/dashboard/overview/overview-movers-panel.tsx`), a per-category MoM breakdown rendered under `OverviewChart` when a bar is clicked. Per-category rows already link to `` `/transactions?months=${year}-${MM}&category=${slug}` ``. There's no other active "filter" on this page to combine: `year` is already embedded in the month string, and the nature chips / cash-accrual lens toggle only affect the chart's own rendering (confirmed against `lib/validations/transactions.ts`'s `parseTransactionFilters` — no lens concept there, and the chips are sub-nature visibility toggles with no single-value equivalent to the `type`/`nature` params). Smallest correct fix: one more link using the same `months=YYYY-MM` pattern, without `category`.

### Task 2: Fix stale client state after "Rimuovi ammortamento" (Bug 2)

**Files:**
- `components/transactions/transaction-table.tsx`
- `tests/transaction-table-amortization-removed-update.test.ts` (new)

**Action:**
1. Extract `markAmortizationRemoved`'s row-update logic into an exported pure helper, `applyAmortizationRemovedUpdate(transactions: TransactionListRow[], transactionId: string): TransactionListRow[]`, placed next to the component's other row-update helpers (`markExpenseDetached`, etc.). On the target row it must clear `amortizationPlanId`, `reimbursementId`, `pairedWithId`, `pairedNetAmount`, `pairedDescription`, `pairedOccurredAt` — the same field list `handleUnpair`'s existing optimistic update already clears, since `reverseDetachTx` deleting the plan's standalone expense cascades away any reimbursement anchored to it (Task 1 makes this reachable via "rimborso", not just "vendita"). It must also clear the same *pairing* fields (not `amortizationPlanId`) on any other row in the list whose `pairedWithId` equals `transactionId` — the refund/sale counterpart — using the same "look up the partner id, then map over the list" pattern `handleUnpair` already uses just above it in this file.
2. Change `markAmortizationRemoved`'s body to `setLoadedTransactions((prev) => applyAmortizationRemovedUpdate(prev, transactionId))`.
3. Add `tests/transaction-table-amortization-removed-update.test.ts` — a plain Vitest unit test (no rendering, no React) importing `applyAmortizationRemovedUpdate` from `@/components/transactions/transaction-table` and `TransactionListRow` from `@/lib/dal/transactions`. Assert: (a) a row with both `amortizationPlanId` and `reimbursementId` set has both become `null` after the update — this is the Bug 2 regression case; (b) a second row whose `pairedWithId` points at the first row has its own `pairedWithId`/`pairedNetAmount`/`pairedDescription`/`pairedOccurredAt`/`reimbursementId` cleared too; (c) an unrelated third row in the list (no relation to either) is returned unchanged (same object reference is fine, doesn't need a deep-equal check beyond field values).

**Verify:**
`yarn vitest run tests/transaction-table-amortization-removed-update.test.ts`

**Done when:** after "Rimuovi ammortamento" on a row that had a linked rimborso/vendita, `computeAmortizationEligibility` for that row (evaluated against the post-update fields) no longer returns `reason: 'reimbursement'` — it falls through to `eligible: true` (or another real guard) without needing a page reload.

## Out of scope

- Any change to "Chiudi per vendita" (`realizePlanTx`) itself — only `reducePlanTx` gains the new call.
- Adding a confirmation/warning to "Rimuovi ammortamento" about losing a linked refund — matches the existing (unwarned) behavior for undoing a realized/sale-linked plan today.
- Threading dashboard nature-chip or cash/accrual-lens state into the new transactions link — no equivalent filter exists on `/transactions`.
- Any change to `parseTransactionFilters` / the transactions route's query-param contract — `months` already supports this.

## must_haves

- `reducePlanTx` calls `createPairTx` with the same anchor shape `realizePlanTx` uses; existing amount/re-spread math and plan status (`open`) are untouched.
- `markAmortizationRemoved` (via `applyAmortizationRemovedUpdate`) clears `reimbursementId` and pairing fields on both the target row and its counterpart, not just `amortizationPlanId`.
- `OverviewMoversPanel` renders a `/transactions?months=YYYY-MM` link for the selected month, independent of the per-category links.
- Each fix ships with a real automated test: Postgres-backed for Task 1, pure-unit for Task 2, static-markup for Task 3.
