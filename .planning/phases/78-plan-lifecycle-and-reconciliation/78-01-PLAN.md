plan, collapsing every remaining (future) instalment onto a single closure-month instalment while

proves the closure-instalment write pattern (new file, new instalment-numbering scheme) that
78-02-PLAN.md directly extends for realize-via-sale — an architectural dead-end here is caught
after one commit, not after three plans.

Purpose: give the user a way to end an amortization plan's accrual lifecycle without ever
rewriting a closed month, and prove the write pattern the rest of Phase 78 builds on.
Output: lib/services/amortization-lifecycle.ts (closePlanTx + shared future-instalment helpers),
lib/actions/amortization-lifecycle.ts (closePlanAction), a confirm dialog wired into both existing

  <behavior>
    - closePlanTx on a plan with future instalments remaining -> deletes those rows, inserts ONE
      new instalment dated exactly at closureMonth whose amount equals the Decimal sum of the
      deleted rows, sets plan.status='closed'.
    - closePlanTx where closureMonth falls in the SAME calendar month as one of the originally
      scheduled instalments -> that instalment is collapsed (treated as future), not preserved.
    - closePlanTx where every instalment's own month is already before closureMonth (0 remaining)
      -> plan.status='closed', zero new instalment rows written.
    - closePlanTx on an already-closed plan -> throws PLAN_NOT_OPEN.
    - closePlanTx on a foreign-owned or nonexistent planId -> throws PLAN_NOT_FOUND, the same
      generic message either way (no ownership-enumeration signal).
  </behavior>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> closePlanAction | untrusted planId crosses the server boundary via a client call |
| closePlanTx -> amortization_plan/amortization_instalment | write scoped by userId, must never touch a foreign plan |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-78-01 | Spoofing/Elevation | closePlanTx | high | mitigate | loadOpenPlanForOwner scopes the initial SELECT by (id, userId) together — a foreign-owned or nonexistent planId resolves to the SAME generic PLAN_NOT_FOUND message, no ownership-enumeration signal |
| T-78-02 | Tampering | closePlanAction | medium | mitigate | ClosePlanSchema (Zod uuid) validates the planId shape before any DB access; verifySession() resolves userId server-side, never trusts a client-supplied userId |
| T-78-03 | Repudiation/Integrity | closePlanTx double-close race | medium | mitigate | loadOpenPlanForOwner's status check plus the delete/insert/update all run inside the SAME db.transaction as the SELECT — a concurrent double-click resolves to PLAN_NOT_OPEN on the second call, never a duplicate closure-instalment row (UNIQUE(planId, instalmentNumber) is a DB-level backstop even if the app-level guard were ever bypassed) |
| T-78-04 | Information Disclosure | ledger_entry_accrual no-live-netting | low | accept | branch 2 never calls a netting fragment on instalment rows by construction (ADR 0019 section 10) — this task adds no new netting logic, only a materialized write, so the risk surface is unchanged from Phase 77 |
