Expand the Phase 78 tracer (78-01-PLAN.md) to deliver AMORT-05 (D-02, realize via sale) and
AMORT-06 (D-03, reimbursement on an open plan reduces+re-spreads) — both requirements share ONE
user-facing entry point (78-CONTEXT.md: "linking a reimbursement/inflow to a transaction that has
an open amortization plan prompts the user to declare intent"), so they ship together in this
plan.

Purpose: let a user recover value from an amortized asset — either by closing it out via a real
sale (netted against the closure month, over-recovery correctly showing as income) or by keeping
the plan open and re-spreading a partial credit across the remaining months.
Output: realizePlanTx + reducePlanTx in lib/services/amortization-lifecycle.ts,
realizePlanAction + reimbursePlanAction in lib/actions/amortization-lifecycle.ts, a new
AmortizationReimburseDialog intercepting the existing "Aggiungi rimborso" flow when the target has
an open plan.

D-03a boundary (do not loosen): AMORT-06 is strictly the amortize-first-then-reimburse order. The
Phase 77 D-04 activation guard (getAmortizationEligibility's 'reimbursement' check, which BLOCKS
*amortizing* a transaction already involved in a reimbursement — the reverse order) stays in force
unmodified. Neither task in this plan touches lib/services/amortization-guards.ts or its
'reimbursement' branch; realizePlanTx/reducePlanTx only ever run against a transaction that is
ALREADY amortized, so D-03a's ordering constraint is honored by construction, not by a new check.

  <behavior>
    - realizePlanTx({userId, planId, saleTransactionId}): loads the plan (open, owned), loads the
      sale transaction (owned) — missing/foreign sale throws TRANSACTION_NOT_FOUND; computes
      closureMonth as the sale's OWN occurredAt (D-02a); collapses future instalments exactly like
      closePlanTx but writes the closure instalment's amount as (Decimal sum of collapsed
      instalments).plus(sale's Decimal amount) instead of the raw sum. SIGN CONVENTION: the sale's
      Decimal amount is the SIGNED transaction amount as stored (an inflow/sale is positive; the
      collapsed cost sum is negative). Example: remaining = -900 (cost) and sale = +1000 (inflow) ->
      closure instalment = -900 + 1000 = +100 (income). Do NOT negate saleAmount before adding.
      Sets plan.status='closed';
      THEN calls createPairTx(tx, {userId, anchor: {transactionId: plan.transactionId},
      counterpartId: saleTransactionId}) to link the sale for cash-lens/bookkeeping purposes.
    - Case: sale magnitude less than remaining magnitude (partial recovery) -> closure instalment's
      net amount keeps the ORIGINAL sign (still a cost, smaller magnitude).
    - Case: sale magnitude greater than remaining magnitude (over-recovery) -> closure instalment's
      net amount FLIPS sign (becomes a positive/income value) — never blocked, never clamped.
    - Case: sale magnitude equals remaining magnitude exactly -> closure instalment amount is
      exactly '0.00'.
    - Case: closing a plan with zero remaining future instalments via realizePlanTx (fully consumed
      before the sale's month) -> no closure instalment row is created at all; createPairTx STILL
      runs (the sale is still linked; conceptually the full sale value becomes pure income since
      there was nothing left to net against).
    - reducePlanTx({userId, planId, refundTransactionId}): loads the plan (open, owned), loads the
      refund transaction (owned) — missing/foreign throws TRANSACTION_NOT_FOUND; rejects
      refundTransactionId === plan.transactionId (self-link) before any other check; computes
      residual as the Decimal-absolute sum of instalments with occurredAt on/after the start of the
      CURRENT calendar month (today, not any date derived from the plan itself); rejects
      (OVER_RESIDUAL, message redirecting to "chiudi per vendita") when the refund's
      Decimal-absolute amount exceeds residual — BEFORE any delete/insert/update.
    - Case: refund amount exactly equals residual -> ALLOWED, all re-spread instalments materialize
      to exactly 0.00 each, plan stays open.
    - Case: refund amount one cent over residual -> BLOCKED.
    - On success: deletes the same future-instalment set the residual was computed from, re-spreads
      via materializeInstalments(newFutureSum, earliestCancelledInstalment.occurredAt,
      cancelledCount) — same instalment count as before, remainder on the first (earliest) new row;
      new instalmentNumbers start at the MINIMUM cancelled number, sequential; updates
      plan.totalAmount by adding the refund's Decimal amount (magnitude shrinks); plan.status stays
      'open'.
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> realizePlanAction/reimbursePlanAction | untrusted planId + counterpart transactionId cross the server boundary |
| realizePlanTx -> createPairTx -> reimbursement/reimbursement_refund | a NEW cross-table link is created from two independently-loaded ids |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-78-05 | Tampering/Elevation | realizePlanTx | high | mitigate | the sale transaction is loaded scoped by (id, userId) BEFORE use — a foreign-owned saleTransactionId throws TRANSACTION_NOT_FOUND, never silently netted against another user's plan |
| T-78-06 | Tampering/Elevation | reducePlanTx | high | mitigate | the refund transaction is loaded scoped by (id, userId) the same way; the refund's amount is ALWAYS read server-side from the loaded row, never trusted as a client-supplied string |
| T-78-07 | Tampering | reducePlanTx self-link | medium | mitigate | explicit refundTransactionId === plan.transactionId rejection before any read of its amount — prevents a self-referencing transaction from corrupting the base instead of reducing it |
| T-78-08 | Integrity | realizePlanTx cross-user pair | high | mitigate | createPairTx's own pre-existing ownership/self-pair/sign-invariant checks (assertInflowRefundAmount/assertOutflowAnchorAmount, reimbursement-invariant.ts) apply unmodified — reusing the v2.8 mechanism inherits its proven guards, no bypass surface introduced |
| T-78-09 | Repudiation | realizePlanTx/reducePlanTx atomicity | medium | mitigate | every write (collapse/insert/update, then createPairTx for realize) runs inside ONE db.transaction — a failure at the link step rolls back the collapse too, never leaving a closed-but-unlinked plan |

</threat_model>
