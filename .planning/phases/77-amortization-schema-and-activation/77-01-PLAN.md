<task type="checkpoint:decision" gate="blocking">
  <name>Decision: plain VIEW vs materialized VIEW for the ledger_entry seam</name>
  <decision>
    D-11 (ADR 0019 SS10, CONTEXT.md, one-way) locks the SEAM SHAPE — one swappable row source per
    lens, `ledger_entry_cash` for cash / `ledger_entry_accrual` for accrual — not a `lens` parameter
    threaded through the aggregation functions. That shape is NOT being re-asked here. What is still
    open (RESEARCH.md "Open Questions" #1, explicitly deferred to plan-phase) is the CONCRETE
    Postgres object: a plain VIEW (recomputed on every read) or a MATERIALIZED VIEW (cached, needs an
    explicit refresh strategy). Once the next 9 aggregation call sites (Plans 77-04/77-05) are
    rewritten against whichever shape is chosen here, changing it means touching all 10 call sites
    again plus retiring/adding a refresh mechanism — a real one-way door for THIS specific choice.
  </decision>
  <context>
    STATE.md's Codebase facts already record the seam as "a Postgres view per lens
    (ledger_entry_cash, ledger_entry_accrual), not a Drizzle CTE aliased as transaction" — so the
    object IS a real `CREATE VIEW`/`CREATE MATERIALIZED VIEW`, generated via `drizzle-kit generate`
    from a `pgView(...).as(sql...)` / `pgMaterializedView(...).as(sql...)` definition in
    lib/db/schema.ts. The amount-resolution SQL is a self-contained copy of
    lib/dal/transaction-pairs-sql.ts's effectiveAmount()/isNotSecondary() CTE (duplicated inline,
    not imported, since drizzle.config.ts pins the schema to lib/db/schema.ts alone — importing the
    DAL helper would create a schema.ts -> lib/dal -> schema.ts cycle).
  </context>
  <options>
    <option id="plain-view">
      <name>Plain VIEW (pgView)</name>
      <pros>Always fresh (no staleness risk); no refresh job/trigger to build or forget; identical
      query cost to today's baseline (the CTE already ran inline on every aggregation call before
      the seam existed — a view just names the same computation, it does not add cost); simplest to
      generate and migrate via drizzle-kit.</pros>
      <cons>Recomputes the reimbursement-netting CTE on every read, same as today — no caching
      benefit if the CTE ever becomes a measured bottleneck.</cons>
    </option>
    <option id="materialized-view">
      <name>Materialized VIEW (pgMaterializedView)</name>
      <pros>Reads become a plain table scan — faster if the CTE is ever proven to be a bottleneck.</pros>
      <cons>Requires an explicit REFRESH strategy (trigger-based on every transaction/reimbursement
      write, or a cron) that this phase has no infrastructure for; a forgotten/delayed refresh means
      the dashboard silently shows stale totals — the opposite of LENS-03's byte-identical guarantee;
      no measured performance problem exists yet to justify the operational cost.</cons>
    </option>
  </options>
  <resume-signal>Select: plain-view or materialized-view (RESEARCH.md and this plan recommend
  plain-view — no measured need for caching, and it keeps LENS-03's byte-identical guarantee trivially
  true by construction).</resume-signal>
</task>
